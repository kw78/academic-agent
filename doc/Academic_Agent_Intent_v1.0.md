# Academic Agent — 项目 Intent 与方向约束

**版本：** v1.0  
**日期：** 2026-10-27  
**文档定位：** 项目方向基线（高于功能 PRD 与架构 Spec）  
**状态：** 可用于后续需求、架构与开发评审

> **一句话定义：** 构建一个以可靠自动化为主体、按需使用 Agent、能够根据个人需求持续扩展的助手系统；以大学生学业管理为首个可用场景。

---

## 1. 为什么做这个项目

大学生的课程、作业、考试、资料和时间安排分散在不同平台；重复查询、抄录、整理和更新信息消耗精力。传统待办应用要求大量手工维护，纯聊天式 AI 又缺乏稳定的长期业务状态，容易把无需推理的重复任务也交给模型执行。

我们希望让系统**持续维护可靠的个人状态，主动完成已经知道怎么做的事情，在确实需要理解或探索时才使用智能能力**。用户获得的应是一个可以长期使用的助手，而不是每次都从零开始的对话。

## 2. 产品愿景及定位

**长期理念（B）：** 通用的、可个性化、可扩展的个人助手。不同用户可以因需求不同而拥有不同的自动化流程、工具与智能能力。

**首个 MVP（A）：** 一名大学生的个人学业助手。先可靠管理课程、作业、考试、学习任务和计划，再验证其他扩展场景。

这不是两个互相竞争的方向：**底层理念保持通用，首期产品范围必须专注。** 不为“将来什么都能做”而牺牲眼前的可用性。

我们不把项目定位为：纯聊天机器人、AI 代写作业工具、自动生成插件的展示项目、预先包含所有功能的庞大平台，或必须始终联网调用大模型才能工作的待办系统。

## 3. 必须坚守的八项原则

### I-01 自动化优先，智能按需

能由已知规则、脚本或算法可靠完成的工作，应直接自动完成。需要语义理解、复杂推理、未知环境探索或特殊能力开发时，才进入 Agent。

**判断标准是任务性质，不是用户是否通过聊天窗口提出任务。** 简单查询和状态修改不应被人为升级为多轮 AI 工作流。

### I-02 智能成果优先沉淀为可复用能力

当 Agent 协助解决未知问题后，只要解决方案可以被验证和重复执行，就优先沉淀成普通配置、脚本或稳定工作流。后续执行不重复消耗模型推理。

**不是让 AI 永远参与，而是尽可能让同一个问题只需 AI 研究一次。**

### I-03 持久事实与会话交互分离

课程、作业、考试、用户完成状态和确认的计划属于业务事实，不能仅存储在对话记忆里。聊天记录可以帮助理解意图，但不能代替学业系统的权威状态。

重要变化应当有清晰的来源和历史；用户能够知道什么改变了、为什么改变。

### I-04 小而稳定的核心，可卸载的功能

长期稳定的业务规则和个人状态由核心负责。采集、规划、提醒、教学、界面等属于可替换的能力。功能模块的增加、禁用和卸载不应破坏核心业务事实。

可扩展**不是把每个函数都做成插件**。新需求先检查能否通过配置或普通脚本满足，只有需要新的独立能力时才增加插件。

### I-05 用户拥有最终控制权

用户能够了解数据从何而来、同步是否成功、计划为何调整，并可以手动修改安排、暂停自动化或停用扩展。

未经授权，不允许系统替用户提交作业、进行考试、修改第三方账户或安装有较高权限的未知代码。

### I-06 可靠性高于表面上的自主程度

数据不能因为抓取失败而丢失；不能重复生成同一份作业；不能把推测当成源平台事实；不能把不可执行的计划呈现为确定可行。

**确定性执行、失败可见、可恢复、可测试，比“全自动”更重要。**

### I-07 保持低耦合，但避免过度工程化

长期要能更换数据来源、规划策略、模型和通知渠道；MVP 不需要提前建设插件市场、分布式微服务、多用户平台或复杂自治系统。

系统应随实际需求演进，而不是围绕假想的未来需求无限抽象。

### I-08 价值由用户结果决定

衡量成功的标准是用户是否减少了重复劳动、是否准确掌握待办、是否能合理安排学习，以及在需要时是否获得有效帮助；不是插件数量、Agent 调用次数或架构复杂度。

## 4. 用户最终应该获得的体验

用户第一次使用时，添加课程或受支持的课程数据源，设置基本空闲时间。系统获取作业和考试信息，形成统一的任务视图。

之后，系统按约定周期自动更新数据。新作业出现或截止时间发生变化时，系统更新相应记录并在必要时调整或提示调整计划；普通同步过程不需要用户打开聊天，也不需要调用 AI。

用户可以随时查看“今天该做什么”“本周哪几项最紧急”，修改任务完成状态或锁定某个学习时段。系统尊重用户调整，发现时间不足时明确解释冲突。

遇到课程疑问、模糊目标、复杂复习安排或未知平台时，用户可以请求 Agent 帮助。Agent 利用已有状态和工具处理问题，但其推断或建议不会未经校验就变成权威数据。

## 5. 首个 MVP 的严格范围

**MVP 必须做到：**

1. 添加和管理课程及至少一个受支持的数据源。
2. 自动和手动同步作业、考试、测验等学业事项。
3. 保存来源、截止时间、完成进度及必要的变更历史。
4. 正确识别新增、修改、重复数据，并保留失败前的有效状态。
5. 根据可用时间、截止日期和用户偏好给出基础学习安排。
6. 允许用户修改、确认、锁定计划及更新任务状态。
7. 提供简单的截止提醒和自动化运行状态。
8. 支持自然语言查询、题目讲解及必要的智能辅助。
9. 重启应用后，数据、配置、计划和后台任务仍可恢复。
10. 常规同步、去重、提醒与基础规划无需 AI 参与。

**MVP 明确不做：**

- 适配任意未知学校网站的全自动通用爬虫。
- Agent 自动设计、安装和维护 Cordis 插件的完整闭环。
- 自动完成或提交作业，以及无人监督的高风险操作。
- 全学科教学引擎、完整知识图谱、复杂学习能力评估。
- 多用户 SaaS、跨端实时同步和独立移动应用。
- 为展示技术而开发与学业目标无关的扩展能力。

首期优先单用户、本地可用，允许先从受控或公开的测试数据源开始，再验证真实平台。

## 6. 能力扩展的方向与边界

系统需要长期具备可扩展性，但**可扩展性是一种系统性质，而非每次任务都要执行的工作流**。

对新需求按照以下顺序处理：

1. **已有能力：** 直接调用或组合。
2. **配置变化：** 调整规则、参数、个人偏好。
3. **简单新自动化：** 增加可验证的脚本或适配器。
4. **智能分析：** 遇到未知、模糊或复杂问题时调用 Agent。
5. **新增插件：** 仅当现有模块无法承载新的独立能力时，才开发并审查插件。

新增能力应可发现、可启用、可停用，必要时可撤销；其生命周期不能不合理地绑死其他功能。用户业务数据不属于可被随意删除的插件临时资源。

## 7. 数据与事件的方向性约束

项目已选择**以领域事件记录重要状态变化，并由其维护或重建当前状态**的思路。这一选择服务于可追溯、可恢复及新增插件利用历史数据的目标。

但并非所有日志、缓存、抓取过程或文件都需要事件溯源；也不能假定事件架构天然消除一切一致性问题。核心业务变化须经验证，普通功能插件不得绕过业务规则直接修改权威事实。

**历史事件是业务事实的基础；用户看到的当前状态应准确、及时、可解释。**

## 8. 已确定的架构方向（仅作为约束，不在本文展开实现）

- 基于 **DSH Harness / Cordis**，复用现有插件和 Agent 运行能力，不另造完整 Harness。
- 采用**稳定领域内核 + 可插拔功能模块**的整体组织方式。
- 核心业务状态采用 **Event Sourcing** 思路，面向查询提供当前状态。
- 后台自动化独立于 Agent 会话；Agent 不充当所有任务的默认调度器。
- 数据源优先通过可验证的适配器和普通脚本扩展。
- 插件生成、安装和高权限执行是特殊能力，受测试和授权约束。

本文不规定数据库表、程序语言、接口签名、消息队列或具体部署配置；这些由架构 Spec 负责。

## 9. 需求与技术决策发生冲突时的优先级

按以下顺序取舍：

1. **数据安全、用户授权与业务正确性。**
2. **MVP 的真实可用性。**
3. **自动化的确定性、低运行成本及故障恢复。**
4. **清晰的模块边界和可持续扩展。**
5. **开发效率、实现简洁性。**
6. **额外的自主性、功能丰富度和技术新颖性。**

例如，某方案能让 Agent 更自主，却要求每次定时同步都调用大模型，应拒绝；某方案能提高插件自由度，却允许插件绕过核心规则损坏数据，也应拒绝。

## 10. 迭代路线

**阶段一：稳定学业 MVP。** 完成数据接入、同步、任务管理、基础规划与按需智能辅助，形成可以日常使用的闭环。

**阶段二：自动化扩展。** 增加更多平台适配器、常用脚本、工作流及错误恢复能力；必要时让 Agent 辅助探索并生成候选脚本。

**阶段三：学业能力深化。** 引入课程资料处理、个性化复习、学科工具及更细致的学习反馈。

**阶段四：通用个人助手。** 保持核心理念，逐渐拓展新的个人事务领域，并形成可复用、可组合的能力生态。

后续阶段不能成为首阶段延迟交付的理由。

## 11. 项目成功标准

**首期成功**不以自动创建插件为门槛，而以一个真实可靠的学业闭环为门槛：用户接入课程信息后，能够持续获取最新待办、安排学习、管理进度，并在需要时获得智能帮助。

关键验收现象包括：

- 同一份作业重复同步不会重复出现。
- 截止时间变化能够被正确发现和处理。
- 网络或解析失败不会破坏原有有效数据。
- 自动化任务不依赖持续开启的 Agent 会话。
- 任务完成和计划修改可持续保存，重启后仍然存在。
- 用户可以暂停某种功能，而核心学业信息仍可访问。
- 对需要推理的学习问题可以调用 Agent；不需要推理的工作不滥用 Agent。

**长期成功**体现为：新需求主要通过能力组合、配置或扩展实现，而不是反复修改核心；新增能力可靠复用，系统仍然可理解、可维护、可控制。

## 12. 评审用方向检查清单

在提出新的需求、架构方案或插件时，先检查：

- [ ] 是否直接解决用户的真实问题？
- [ ] 是否属于当前阶段，而非提前实现远期设想？
- [ ] 能否使用已存在的确定性能力？
- [ ] 如需 AI，是否存在真正的理解或推理需求？
- [ ] 是否保持学业业务事实的权威性和可恢复性？
- [ ] 是否让用户清楚知道重要变化与风险？
- [ ] 是否允许相关功能独立演进或停用？
- [ ] 是否引入了可以避免的复杂度、权限或长期维护负担？
- [ ] 是否具备可检验的用户结果？

若某项技术设计与本文冲突，必须明确解释其必要性；不得以“更智能”“更通用”“更先进”为唯一理由。

## 13. 与其他文档的关系

| 文档 | 回答的问题 | 适用范围 |
|---|---|---|
| **Intent（本文）** | 为什么做、做成什么样、哪些原则不能变 | 产品方向与评审最高基线 |
| **PRD** | 用户需要哪些能力、MVP 要交付什么 | 产品功能与业务验收 |
| **Architecture Spec** | 用什么结构和机制实现、如何保证一致性与扩展性 | 技术设计与实现约束 |
| **实施计划与测试** | 先做什么、如何验证、何时交付 | 开发推进与质量检查 |

需求可以增加，技术方案可以重构，但不能在没有明确理由的情况下偏离 Intent。

---

## 北极星原则

> **让普通程序可靠地完成重复工作，让 Agent 处理真正需要智能的问题，让系统通过可控的扩展能力持续适应用户。**  
> **B 的理念，A 的 MVP；先有稳定可用的产品，再有更丰富的自主能力。**
