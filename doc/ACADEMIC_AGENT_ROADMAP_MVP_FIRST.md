# Academic Agent Roadmap — MVP First

> 目标：以最快速度交付可用 MVP，再通过短迭代扩展。
>
> 本文不按日期、周数或月份规划。所有工作按依赖关系、验收门槛和优先级推进。
>
> **执行原则：一天内完成 MVP 的目标是压缩范围，不是降低安全、数据正确性或验收标准。**

## 1. 产品目标

Academic Agent 是构建在 DSH 上的可扩展个人学业助手。DSH/Cordis 提供插件化宿主与 Agent 扩展能力；Academic Agent 提供学业领域能力、数据持久化、数据源接入和确定性自动化。

核心工作流：

1. 用户在 DSH Desktop 中添加课程平台网址。
2. 用户通过浏览器完成平台登录；系统安全保存会话并验证登录状态。
3. 系统读取经授权的页面证据。已知平台优先使用已有 Adapter；未知平台由 Agent 在确有必要时生成声明式 Adapter 候选。
4. 候选必须经过确定性校验、样本验证和数据预览；用户确认后才启用。
5. Adapter 读取课程、作业、考试等学业数据，经 Connector 和 Kernel 写入本地事件存储。
6. 系统根据已持久化的数据自动整理任务、截止时间、提醒与学习计划。
7. 用户可以查询和理解自己的学业信息；需要推理、解释或特殊适配时才调用 Agent。
8. 重复同步不产生重复事项；登录失效或解析失败时保留已有有效数据，并明确提示问题。

## 2. MVP 的严格定义

MVP 不是“每个模块都存在”，而是用户能独立完成一条端到端流程。

### 必须交付的用户体验

- DSH Desktop 能加载 Academic Agent UI 和后台 Host。
- 用户能添加一个已有支持的平台，并通过浏览器完成登录。
- UI 能区分数据源配置状态、登录状态和最近同步状态。
- 用户能触发验证、预览和同步，并看懂结果。
- 至少一个真实平台能够稳定同步可访问的课程与作业。
- 考试/测验：有真实可访问样本时必须验证；若测试账号没有此类数据，必须用 fixture 验证解析逻辑，并在 UI/文档中如实标注“真实环境尚未验证”，不得伪造已验证状态。
- 同步数据经过现有 Connector/Kernel/Event Store 路径持久化；不得由 UI、Agent 或 Adapter 直接写业务表。
- 重复同步正确去重；失败或部分结果不能清空最后一次有效数据。
- 用户能看到任务列表、截止信息和基本计划/提醒。
- 用户可以让 Agent 基于已保存的学业数据进行解释或回答问题；普通同步、去重、提醒和基础规划不依赖 LLM。
- 凭据不出现在普通配置、事件、日志、UI 返回值或模型上下文中。

### MVP 对扩展性的最低证明

不要求首版支持所有学校，但必须证明扩展路径不是空架子：

- 已有平台通过可信 Adapter 接入。
- 至少一个声明式 Manifest 能通过统一 Runtime 完成提取、标准化和同步。
- Agent 生成的内容只是候选，不自动获得网络权限或启用资格。
- 候选通过统一验证、预览和用户确认后，才能成为活动版本。
- 新平台的普通抓取和映射不应要求修改 Kernel 或复制一套 Connector。

### MVP 明确不做

- 不执行任意 AI 生成的 JavaScript、shell 或任意代码。
- 不追求输入任意 URL 后零人工介入、自动探索整个网站。
- 不做通用爬虫平台、插件市场或多用户云服务。
- 不扩展到大量新平台；先把一个真实平台跑通。
- 不在 MVP 中实现附件下载、成绩、提交历史、自动提交作业等非必要功能。
- 不为了“架构更漂亮”重写 Event Store、Kernel、Connector、Scheduler 或 DSH 集成。
- 不把 XPath、复杂脚本沙箱、多页自动采样等能力当作 MVP 阻断项，除非现有目标平台确实无法通过已有能力接入。

## 3. 执行规则：先闭环，后扩展

1. **冻结范围。** 本轮只接受能直接阻断 MVP 验收的改动。
2. **先复现，再修改。** 每个缺陷必须有复现步骤或失败测试，不做猜测性重构。
3. **一次打通一条垂直链路。** 从 UI 操作开始，经过 Host、Adapter、Connector、Kernel、Event Store，最终在 UI 看到正确结果。
4. **优先复用现有实现。** 能修现有模块就不新增模块；能用声明式规则就不写专属执行器。
5. **测试与文档跟随代码。** 不允许先把 Roadmap 打勾，再补测试或手工验证。
6. **每轮只做一个最小变更集。** 改动后立即执行相关测试；完成一组后再跑完整检查。
7. **失败就缩小问题。** 不因一个平台问题扩展整个架构。
8. **所有非阻断事项进入停车场。** 不得在实现过程中临时增加“顺手做一下”的功能。

## 4. 按依赖关系推进的 MVP 路线

### Gate 0 — 真实基线

**目的：确认现在的代码究竟能运行到哪一步。**

执行：

- 核对当前 Git 分支、提交和工作区；不覆盖用户未提交的改动。
- 安装依赖，运行类型检查、单元/集成测试、DSH 构建和 UI 构建。
- 在独立测试数据库启动 DSH Desktop 或项目已支持的桌面运行配置。
- 记录每条检查的真实结果；旧文档中的测试数量只能作为历史记录。
- 按“通过 / 失败 / 未运行 / 需要真实账号”分类，不把未知写成通过。

验收：

- 有一份可重复执行的验证清单。
- 已知失败能复现，且与未运行的检查明确区分。
- 不因基线检查顺手重构。

### Gate 1 — 桌面端可启动、可操作

**目的：用户能在真实 DSH Desktop 中使用，而不是只在单元测试里成立。**

执行：

- 启动桌面端，确认 Academic Agent UI 和 Host 均加载。
- 确认 UI 调用的是正确 Host API 和数据库。
- 确认只运行一个使用该数据库的 Host，避免并发打开同一数据库。
- 验证刷新、关闭再打开、禁用/启用插件后的行为。
- 检查连接页面、数据页面和错误状态是否能正常呈现。

验收：

- 无需开发者临时手工改数据库即可完成基本操作。
- UI 与 Host 的状态一致。
- 启动失败、Host 不可用和无数据状态有明确反馈。

### Gate 2 — 真实平台登录与会话

**目的：证明用户能安全地把账号会话交给系统使用。**

执行：

- 用户输入受支持平台的网址。
- 通过独立浏览器上下文完成登录，包括平台实际要求的 SSO/验证码。
- 会话秘密存放于现有安全凭据机制中；UI 只显示状态和脱敏标签。
- 验证必须访问受保护资源，不能把“用户关闭登录窗口”当作认证成功。
- 验证会话过期、登录失败、取消登录和删除会话的状态。
- 确认 Agent prompt、日志、普通配置和错误消息不含密码、Cookie、Token 或敏感 URL 参数。

验收：

- 至少一个真实账号可以完成登录、会话保存和受保护资源验证。
- 删除会话不会删除已同步的学业数据。
- 未验证会话不能进入正式同步。

### Gate 3 — 一个平台的数据同步闭环

**目的：让真实学业数据正确进入本地权威数据模型。**

优先使用现有 Blackboard Adapter，不为首版新建一套平台实现。

执行：

- 同步课程和作业；在真实账号有可访问数据时验证考试/测验。
- 对分页、文件夹、日期、时区、缺失截止时间和外部 ID 做有针对性的测试。
- 预览明确区分新增、更新、未变化、跳过、未返回和警告。
- 正式写入只通过 Adapter → Schema 校验 → Connector → Kernel 命令 → Event Store。
- 同一份数据重复同步应为 no-op；数据变化时应产生确定性更新。
- 网络错误、认证失败、解析错误或部分结果不能删除或覆盖最后一次有效数据。
- 不将“本地未返回”自动等同于“平台已删除”；缺失记录只能按明确策略处理。

验收：

- 一个真实平台可以重复完成登录、预览、同步和再次同步。
- 课程和作业数据在 UI 中可见且字段正确。
- 事件/投影与 UI 查询结果一致。
- 失败与部分同步有明确状态，不会伪报成功。
- 考试/测验的真实验证状态如实记录。

### Gate 4 — 学业任务与基本规划可用

**目的：数据同步后，用户能立即获得实际价值。**

执行：

- 将课程、作业和考试等来源记录映射为现有学业领域模型。
- 任务状态、截止时间和来源可追溯。
- 由确定性逻辑生成基础任务列表和计划；明确报告时间冲突或无法安排的事项。
- 提供必要的提醒和完成状态管理。
- Agent 只能基于已保存数据进行查询、解释和规划辅助；它不能把猜测写成平台事实。
- 不引入新的复杂规划算法，除非现有规划器无法完成首版基本用例。

验收：

- 用户能回答“最近有什么作业”“什么时候截止”“接下来先做什么”。
- 数据变化后，查询和计划能反映新状态。
- 没有 LLM 时，同步、去重、基础排序和提醒仍然可用。

### Gate 5 — 最小 Agent 适配流程

**目的：证明扩展能力能服务产品，而不是成为一个独立研究项目。**

只在已有平台适配器无法满足需求时走这条流程。

执行：

- 用户添加未知平台并完成登录、授权。
- 探测工具只返回必要的结构化证据；默认不把整段原始响应、敏感字段或完整页面正文交给模型。
- Agent 基于证据生成声明式 Manifest 候选。
- 候选经过 schema/权限检查、固定样本回放和真实数据预览。
- 验证失败时给出可定位的错误；允许 Agent 修订候选，但不能自行放宽安全策略。
- 只有用户明确确认后才启用；保留旧版本并支持回滚。
- 已有会话与新数据源的绑定必须经过同站点/授权范围检查，不能隐式跨域复制会话。

验收：

- 至少一个声明式适配器能走完候选、验证、预览、启用、同步流程。
- 候选失败不能影响现有活动版本和已同步数据。
- Agent 无权自行批准候选、扩大域名/路径范围或执行任意代码。
- 如果生成步骤仍需在 DSH 对话中触发，就在 UI 中明确说明；不得宣传为全自动接入。

### Gate 6 — 发布前最小回归

**目的：确认交付物可以被重复使用，而不是只在开发者机器上偶然成功。**

执行：

- 从干净启动流程再走一遍真实用户路径。
- 在独立测试数据库中验证：首次同步、重复同步、数据更新、认证失败、网络失败和恢复。
- 验证备份可生成、恢复流程有明确说明。
- 检查错误信息、日志和 Agent 结果没有泄露秘密。
- 更新 README、运维说明、测试记录和 Roadmap，准确标记真实环境尚未验证的功能。
- 记录已知限制，但不在发布前临时扩大范围。

最终验收：

- 用户能启动应用、添加平台、登录、同步并看到真实学业数据。
- 重复运行不会制造重复事项。
- 失败不会破坏已有数据。
- 用户可以查看任务和基本计划，并获得基于已保存数据的解释。
- 所有写入遵循 Kernel 权威路径。
- 安全边界通过相关回归测试。
- 未通过的项目明确列为未完成，MVP 不得整体标为完成。

## 5. 一天内交付时的取舍规则

这是执行约束，不是按小时排期。

- 只处理 Gate 0–6 中阻断主链路的工作。
- 优先修复一个会阻止用户完成流程的问题，不并行开发多个新能力。
- 若某一项不影响首个受支持平台的完整闭环，记录为后续项。
- 若某一项涉及凭据泄露、越权网络访问、数据损坏或错误同步，则不能用“先发布再说”处理。
- 若某项真实环境条件不可获得（例如账号没有考试样本），使用 fixture 验证代码逻辑并明确标记真实验证缺失；不得制造假数据来声称通过。
- 如果剩余工作超出一天内的合理范围，继续缩小 MVP 的非核心范围，而不是删掉安全检查或虚报验收。

## 6. MVP 通过后再做的扩展

以下项目不阻塞 MVP，只有真实使用需求出现时才启动：

### 数据源扩展
- 自动发现相关页面与分页入口。
- 更多 LMS/教务平台的声明式 Manifest。
- 更丰富的字段转换、XML/XPath 或平台特定解析能力。
- 附件、成绩、提交历史等数据类型。
- 平台改版检测和候选修复建议。

### Agent 与自扩展
- 更连贯的候选生成 UI，减少在 UI 和 DSH 对话间切换。
- 自动采集多个授权页面的结构化样本。
- 基于失败证据提出修复候选，并与上一个稳定版本比较。
- 仅当声明式能力被真实用例证明不足时，评估隔离脚本执行能力。
- 任意代码执行若未来实施，必须有独立进程/容器、网络白名单、资源限制、超时、只读输入和统一契约；不得直接在主进程中执行模型输出。

### 学业助手能力
- 更精细的学习计划、时间冲突优化和个性化规则。
- 更丰富的解释、复习辅助和跨课程分析。
- 用户偏好和规则的可配置化。
- 通知渠道扩展和可观测性改进。

### 工程能力
- 完整的事件重放与投影重建演练。
- 更系统的迁移兼容和备份恢复测试。
- 插件启停、升级、回滚和文件级 HMR 的真实桌面验收。
- 多平台、多数据源的性能与故障注入测试。

## 7. 永久架构约束

- **DSH 是可扩展宿主**：Academic Agent 应复用 DSH/Cordis，不另造一套插件宿主。
- **Kernel 是学业业务权威入口**：UI、Agent、Adapter、调度器不得绕过命令入口写业务状态。
- **Event Store 是事实源**：核心事件与必要投影更新保持事务一致；可重建投影不得反向成为事实源。
- **确定性自动化优先**：常规同步、分页、去重、提醒、状态转换和基础规划使用普通代码。
- **Agent 按需介入**：用于页面结构理解、候选生成、异常分析、解释和特殊需求；模型输出不是权威事实。
- **声明式优先**：新网站优先新增/修复 Manifest，不复制核心逻辑；只有明确的表达能力缺口才考虑代码执行。
- **候选与活动版本分离**：生成、验证、审批、启用和回滚必须是可区分状态。
- **凭据与业务数据分离**：密码、Cookie、Token 不进入事件、普通配置、日志或模型上下文。
- **失败可恢复**：失败、空结果、部分同步不能静默清空最后一次有效数据。
- **不为抽象而抽象**：没有实际需求和验收用例，不新增层、框架或抽象。

## 8. 当前任务停车场

以下事项不应抢占 MVP 主链路，除非复现后证明它们是阻断项：

- 任意 JavaScript/脚本沙箱。
- 新增第三、第四个真实平台。
- 完整多页自动采样。
- 附件下载、成绩和提交历史。
- 复杂规划优化。
- 大规模模块重命名或目录重组。
- 非必要的 Event Store/Kernel 重构。
- 仅为完善文档而增加的非阻断文档体系。

注意：安全漏洞、凭据泄露、越权抓取、事件/投影不一致、数据重复或丢失，不属于可延期的“停车场”事项。

## 9. 每轮迭代的完成定义

一个工作项只有满足以下条件才算完成：

- 有明确的用户价值或阻断问题。
- 有可复现的测试或验收步骤。
- 实现范围最小，没有夹带无关重构。
- 相关自动化测试通过。
- 涉及 DSH Desktop、浏览器会话或真实平台的能力已做真实环境验证；若条件不可用，则明确标记为未验证。
- 文档与代码状态一致。
- 失败行为和回滚/恢复行为已考虑。
- 没有把“代码写完”当成“产品交付”。

## 10. 最终方向

先把一个真实平台的学业数据可靠地带入本地系统，让任务、截止时间、规划和解释真正可用。然后再通过 DSH/Cordis 的扩展机制，逐步增加更多平台和特殊能力。

**近期成功标准不是模块数量、抽象层数量或测试总数，而是用户能否独立完成一条可靠、可重复、可解释、不会破坏已有数据的完整流程。**
